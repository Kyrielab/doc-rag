# 语料卫生大于算法调优：一次所有"高级手段"都零收益的 RAG 检索优化记录

> 项目：[doc-rag](https://github.com/Kyrielab/doc-rag) —— 技术文档混合检索问答服务（Java 21 / Spring Boot 3 / Elasticsearch / 阿里云百炼）
> 本文所有数字来自 `experiments.md` 与 `eval/result-*.json`，可复现。

## 起点：一个诚实的评测集

优化之前先建衡量能力。48 条评测用例，三层结构：

- 30 条术语题（题面与文档用词重合）
- 13 条口语化改写题（题面刻意避开文档原词，如"程序突然断电了，内存里还没写到磁盘的数据怎么办"）
- 5 条拒答题（语料外主题，验证系统会不会不懂装懂）

每条标注 **chunk 级金标短语**（正确 chunk 独有的词，如 `redo`、`间隙锁`），短语在语料中的唯一性用脚本验证过——不验证会埋进假金标：`SYN` 撞上 synchronized 的子串、`QUIC` 撞上 Redis 的 quicklist、`React` 撞上 Reactive。

主指标 ContentRecall@8 = 金标短语出现在 top-8 检索结果内容中的比例。为什么不用文档级召回？实测过：7 篇文档的小语料上，"随便哪篇对文档的随便哪个 chunk 进 top-8"几乎必然发生，三个配置全部 1.0，零区分度。**指标饱和时，第一反应应该是怀疑指标，而不是庆祝。**

基线（混合检索 = BM25 + 向量双路并行 + RRF 融合）：

| 配置 | ContentRecall@8 |
|---|---|
| 纯关键词 | 0.884 |
| 纯向量 | 0.953 |
| 混合 | 0.953（失败集与纯向量不同：救回 1 条、丢掉 1 条） |

混合与纯向量打平但失败集互补——这个细节后面有用。当时的两条漏检：`network-01`（TCP/UDP 区别）和 `para-03`（断电后数据怎么办）。

## 军火库挨个上阵，全部零收益

按教科书顺序，我把检索优化的"标准答案"全试了一遍。每次只改一个变量，同一套用例：

| 手段 | 预期 | 实测 |
|---|---|---|
| 交叉编码器重排（gte-rerank-v2） | 修复排序 | **0.953 → 0.953**，零收益 |
| LLM 查询改写（qwen-turbo） | 修复词面失配 | **0.953 → 0.953**，还 +402ms/查询 |
| rrfK 10 / 60 / 100 | 放大头部权重 | 三个值全部 0.953 |
| 向量路权重 1x / 2x | 偏向更强的一路 | 0.953 |
| 相似度阈值 0.2 / 0.35 / 0.5 | 放宽候选 | 0.953 |

五个方向，十几次实验，指标纹丝不动。如果是"调参→看整体分数"的工作方式，这里大概率会得出结论"重排没用/改写没用"，然后换个模型再试。**逐用例归因**给出了不同的答案：

- **重排零收益的原因**：`para-03` 的金标 chunk 压根没进任何一路的 top-30 候选——重排只能重排已召回的候选，救不了召回失败。`network-01` 的金标进了候选池，但重排把其他 TCP/UDP 对比 chunk 排得更高（那些 chunk  arguably 更能回答问题——这是金标过窄，不是系统错）。
- **改写零收益的原因**：把线上真实改写输出拉出来看，"程序突然断电了…"只被改写成"程序突然断电内存中未写入磁盘的数据如何恢复"——语法整理，没有术语注入。因为**问题本身没说清是 Redis 还是 MySQL**，改写模型无从猜测领域。而口语化题的词面鸿沟（para-08/para-12）早就被向量检索覆盖了，轮不到改写帮忙。

结论：两条漏检，一条是评测集缺陷（问题领域歧义），一条是金标设计问题。**检索栈已经触及评测集的天花板，继续调参是无用功。**

## 转机：top-3 里一个不该出现的 chunk

归因 `network-01` 时，我把该查询的 top-3 检索结果原文打了出来。第三名是这样的东西：

```
ET vs POST,应用层协议,网络分层,队头阻塞,PING命令,ARP协议 ---
```

这是文档开头的 **YAML frontmatter**——`content: 计算机网络面试题,TCP/IP四层模型,HTTP面试,HTTPS vs HTTP,…` 这种给 SEO 用的关键词堆叠元数据，被我的解析器当正文切进了索引。

它是一段"万能磁铁"：关键词密度极高，几乎对任何查询都能拿到不错的 BM25 分数，于是常驻各路 top-N，把真正的正文 chunk 挤出窗口。回头看，纯关键词基线里那几条莫名其妙漏检（`redis-03`、`para-08`、`para-12`），凶手很可能都是它。

修复是 20 行解析代码：切分前剥离 `---` 围栏的 frontmatter 块（含 CRLF 兼容、围栏不闭合不吞正文的边界处理，4 个单测钉住）。重灌语料（568 → 561 chunks），重跑评测：

| 配置 | 剥离前 | **剥离后** |
|---|---|---|
| 纯关键词 | 0.884 | **0.953（+6.9pp）** |
| 混合 | 0.953 | 0.953 |
| 纯关键词延迟 | 57ms | **15ms** |

之前漏的三条全部复位。**重排、改写、调参加起来没做到的事，一次语料清洗做到了。**

诚实的另一面：干净语料上，混合检索对纯关键词的实测优势也归零了（0.953 = 0.953，失败集相同）。混合的价值从"可测的召回优势"变成了"词面失配场景的保险"（+195ms）。我没有删掉混合检索——保险的价值在评测集覆盖不到的长尾查询上——但**我不会再拿旧数据宣称混合比词法强 6.9pp**，那句话只在脏语料上成立。

## 复盘：四条方法论

**1. 评测框架是唯一的前提。** 没有 chunk 级金标，frontmatter 磁铁的伤害会摊薄在"整体分数不高"里；没有逐用例的 retrieved ids，我不可能看到 top-3 里那段不该出现的文本。所有"优化有效/无效"的判断，都是评测框架的输出。

**2. 先归因，再开药。** 五个手段零收益不是"技术不行"，是药不对症：重排治排序，不治召回；改写治词面，不治歧义。归因分类（检索失败/融合失败/生成失败/标注可辩）让每一次"无效实验"都变成了信息。

**3. 数据质量 > 算法复杂度。** 检索系统的第一性问题是"索引里放的是什么"。关键词堆叠的元数据、页眉页脚、导航栏——这些内容进索引就是投毒。清洗语料的收益常常吊打模型升级。

**4. 零收益实验要原样记录。** 我的实验日志里躺着五次失败：重排、改写、rrfK、权重、阈值。它们的价值是划定边界——"此路不通"和"此路通"同样是结论，而且前者能防止下一个人（包括未来的我）再交一遍学费。

## 附：复现

```bash
git clone https://github.com/Kyrielab/doc-rag && cd doc-rag
docker compose up -d                 # ES / Redis / PostgreSQL / RabbitMQ
export LLM_API_KEY=你的百炼key        # OpenAI 兼容端点均可，改 application.yml
mvn spring-boot:run
# 灌入 corpus/ 里的文档后：
curl -X POST "http://localhost:8080/api/eval/run?label=repro&topK=8&skipGeneration=true&casesFile=eval/my-eval.jsonl"
```

评测集、原始报告 JSON、九个配置的实验矩阵脚本都在仓库里。数字对不上欢迎提 issue——那说明你又发现了一个我没人发现的变量。
